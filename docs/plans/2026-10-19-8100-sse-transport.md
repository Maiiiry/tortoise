# Plan — #8100: SSE as a second transport on the ONE delivery layer

**Issue:** #8100 · **Epic:** #2080 (W4 delivery, phase 2) · **Branch:** `feat/8100-tm`
**Depends on:** the merged #2081 delivery layer (`tortoise/webhook_delivery.py`, commit `f84dbffac`)
**Status:** COMPLETE for the transport + sharing half; the #3909 **trigger surface** stays owner-gated (§6).

---

## 1. Confirmed problem (RE-MEASURED on this branch, not inherited)

The issue body's one factual claim about the starting state is: only webhook shipped, SSE did not.
Measured on this branch (`git rev-parse HEAD` at start of work):

```
$ grep -rn "event-stream\|SseTransport\|SSETransport" --include=*.py tortoise/ | grep -v mcp
(no hits: every text/event-stream hit is the MCP streamable-http tool transport)
$ grep -rn "def dispatch_pending\|backoff_seconds(" --include=*.py tortoise/
tortoise/webhook_delivery.py  (one drain, one backoff)
```

So the delivery layer is ONE module with ONE drain, and **no SSE transport exists** — the gap is
real and this is not `ALREADY_FIXED`. The webhook half ships (4 tenant REST routes, subscription
registry with a durable `cursor`, retry/backoff, receipts); an app that cannot hold a poll loop can
be *pushed* to, but only over a URL **it hosts**. A browser/dashboard app has no such URL — SSE is
the only shape that reaches it, and it is the transport #2081's own scope named and did not ship.

**Root cause, as a design question:** SSE is not a second delivery *system*. An SSE subscriber needs
the SAME event stream, the SAME cursor bookkeeping, the SAME retry policy and the SAME receipts. The
only thing that differs is the SINK. So the fix is a second `transport` implementation behind the
existing dispatch contract, plus a stream surface that serves the durable event log — **not** a
second dispatcher.

## 2. The design decision that makes it one layer, not two

The dispatch contract is `post(url, body, headers) -> (status, error)`; a 2xx advances the cursor.
An SSE transport cannot POST anywhere, so what does its 2xx *mean*?

**Decision: 200 means "this event is now on the subscriber's stream", and the buffer is the DURABLE
`:GraphEvent` log, not process memory.** Consequences, all of which are the reason for the choice:

* **No in-process queue.** A queue in the dispatching worker is invisible to a stream served by a
  *different* worker (multi-worker deployments) and dies with the process. The durable log is
  already written by `event_store` for every mutation and is already what `dispatch_pending` reads.
* **Reconnect cannot gap.** The stream reads `event_store.read_after` from the client's floor, so a
  client that reconnects with `Last-Event-ID: <seq>` resumes exactly after `<seq>` — no gap, and
  duplicates only in the documented at-least-once class (a floor below the cursor replays).
* **The retry path stays the retry path.** An SSE delivery that cannot be accepted is expressible
  as a transport error and is then retried by the SAME `backoff_seconds` / `next_attempt_at` /
  attempt-ceiling machinery — pinned by a test, not by convention.
* **Receipts stay one shape.** An SSE attempt writes the same `:DeliveryReceipt`
  (`delivered`/`retrying`/`exhausted`, `http_status`, `error`, `duration_ms`).

The wake signal is best-effort and **not** load-bearing: `SseBroker` only wakes a stream that is
already polling the durable log (`TORTOISE_SSE_POLL_S`, default 1s), so a lost wake costs at most
one poll interval. Delivery cadence is the dream cycle (the #2081 target "≤ one dream-cycle
cadence"), so a 1s poll bound never becomes the latency floor.

## 3. Rejected alternatives

| Approach | Why not |
|---|---|
| A second dispatcher that writes into a per-subscription in-memory ring buffer | Exactly what the issue forbids (indicator 2). Also worker-local: a stream on another worker sees nothing, and the buffer is lost on restart — a gap by construction. |
| SSE clients poll `GET /v1/events` themselves and call it "SSE" | That is the PULL path that already ships. It adds no transport, and the browser still needs a server-held connection to receive `text/event-stream`. |
| Store an SSE "endpoint URL" like a webhook and POST frames to the client | Not how SSE works: the client opens the connection. A third-party app cannot host an SSE target for us. |
| Make the stream re-derive envelopes from points (`compute_confidence` per frame) | Violates #2081 contract 2 (no EP work on the push path). The envelope is the durable event payload, byte-identical to the webhook body. |
| Defer the stream route and ship only a library | #2081's own learning: "do not file the push path as a contract without a shipped implementation". A transport with no consumer surface is dead code. |

| Piece | Home | Contract |
|---|---|---|

| SSE transport | `tortoise/sse_delivery.py` | `SseTransport.post()` = publish a wake for `<sub_id>` and return `(200, None)`; a malformed `X-Tortoise-Delivery` header returns a transport ERROR (so the shared retry/backoff handles it). |

**Surface statement (deliberate, reviewable):** the MCP tool registry and the public `TortoiseSDK`
surface are **untouched** — the #3863 gate is not approached. The REST route is a THIRD surface,
declared in the #3875 inventory so the growth is visible; that inventory is the mechanism #3875
built for exactly this, and #8100's own scope names the SSE transport as in-scope.

## 6. The #3909 half — design note + the owner-approval question, with its evidence

**Which layer #3909 reuses (this is the answer, not a plan):** the SAME four pieces, unchanged —
`create_subscription` (as the registry, with `transport` now covering both sinks), `dispatch_pending`
(the drain), `backoff_seconds`/`next_attempt_at`/`disabled_at` (the retry policy) and
`:DeliveryReceipt` (receipts). #3909 adds **trigger types**, and trigger types are an *event-source*
question (`event_store` + the `event_types()` registry), not a delivery question — so it must not
add a dispatcher, and there is nothing left for it to reuse-or-implement besides the emission side.

**The owner-approval question for its trigger surface (recorded, not assumed):**

* #3909's own body states the gating rule verbatim — *"any new endpoint or tool requires explicit
  owner approval per the frozen-surface rule, so this cannot add surface by accident."*
* What #3909 needs beyond this layer: (a) new lifecycle/confidence-threshold **event types** emitted
  by the EP/lifecycle write paths, which grow the public event-type vocabulary an agent sees through
  `tortoise_events_poll` / `GET /v1/events`, and (b) a decision on whether threshold subscriptions
  are addressed per point/topic/class (a targeting surface, i.e. new request shape).
* **Neither is decided here.** #3909 is owner-filed as "not prioritised, post-beta — do not schedule
  it without a fresh owner decision", so the correct action for this lane is to leave it gated and
  record the two questions above on #3909 itself (comment posted with this evidence) rather than to
  build a trigger surface.

## 7. Known limitations (stated, not hidden)

1. **Stream lifetime is bounded** (`TORTOISE_SSE_MAX_STREAM_S`, default 300s). The client reconnects
   with `Last-Event-ID`; no gap, but a reconnect per 5 minutes. Needed because a hosted proxy/worker
   slot cannot be held indefinitely.
2. **`Last-Event-ID` is honoured as-is** (not clamped to the subscription cursor). A client that
   claims a future seq receives nothing until newer events arrive; that is the client's claim to
   make, and clamping would silently drop events the client has not seen.
3. **The stream reads the durable log**, so retention applies: `event_store.purge_expired`
   (30 days) bounds how far back a reconnect can replay.
4. **A retry whose backoff elapses while the tenant is IDLE** still waits for the next dream — the
   pre-existing #2081 trigger gap, unchanged by this transport, and unchanged for both sinks.
